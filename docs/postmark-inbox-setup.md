# Postmark inbound setup

Booking confirmations that families forward to their own address end up on the
`/inbox` screen. This document is what has to be true in Postmark, at the DNS
registrar for `trips.alyeska.app`, and on Vercel for that to work.

Each family gets an opaque six-character local part -- for example
`fhc5h4@trips.alyeska.app` -- generated by a Postgres trigger the first time a
family row is inserted. The address is shown on the `/inbox` screen and, more
quietly, on the Trips index and the Family screen. Anything the family forwards
to that address arrives here.

## What the pieces do

| Piece                              | Job                                                             |
| ---------------------------------- | --------------------------------------------------------------- |
| `trips.alyeska.app` MX records     | Point mail for that subdomain at Postmark's inbound MTA         |
| Postmark inbound server            | Receives the mail and posts it to the app as JSON               |
| `POSTMARK_WEBHOOK_SECRET` on Vercel | Shared secret the webhook checks on every request              |
| `/api/inbox/receive`               | The webhook route that stores the message and its attachments   |

Transactional mail continues to send from `alyeska.app` unchanged. The
subdomain is used so a misconfigured MX record on the marketing domain can
never accidentally swallow booking confirmations, and so the transactional
sender's reputation is not affected by whatever inbound spam a public address
attracts.

## Step by step

### 1. Point `trips.alyeska.app` at Postmark

At the registrar for `alyeska.app`, add these MX records on the subdomain
`trips`:

| Host    | Type | Priority | Value                    |
| ------- | ---- | -------- | ------------------------ |
| `trips` | MX   | 10       | `inbound.postmarkapp.com` |

Postmark's inbound domain does not change between servers -- one host is
enough. Do not add A or CNAME records on `trips`; the subdomain exists only to
receive mail.

### 2. Create the Postmark inbound server

In Postmark, create a new Server and choose the Inbound stream. Note the
inbound address Postmark hands out for it -- something like
`abcdef01@inbound.postmarkapp.com`. You do not have to use that address; the
family-specific addresses will forward through the MX records added in step 1.

### 3. Point the inbound webhook at the app

On the same Postmark server, open Inbound → Settings and set the webhook URL
to:

```
https://<production host>/api/inbox/receive
```

The production host is whatever the app is served from -- for a first cut,
`alyeska.app` itself, or the deployment URL Vercel generates. Include the full
path.

### 4. Add the shared secret on both sides

Generate a long random string (32 bytes of base64 works). Save it in two
places:

1. **Vercel** → Project Settings → Environment Variables. Add
   `POSTMARK_WEBHOOK_SECRET` to Production (and Preview if you plan to test
   there). Redeploy so the new environment reaches the running function.
2. **Postmark** → the inbound stream's Settings page. Two options depending on
   what your Postmark account exposes:
   - If the stream Settings page has a **Include custom headers with the HTTP
     POST** section, add a header named `x-postmark-webhook-secret` with the
     same value.
   - If it does not (some accounts do not have that field on inbound streams),
     put the secret directly in the Webhook URL as a query parameter:
     `https://<production host>/api/inbox/receive?secret=<the secret>`. The
     webhook accepts either the header or the query parameter.

The webhook rejects any request whose secret does not match with a 401 and
does not touch the database, so a missing or wrong secret is safe. Because the
query-string secret rides over TLS, it is not visible on the wire; the tradeoff
versus a header is that it can end up in Postmark's activity logs, which is
acceptable since only you and Postmark can see them.

### 5. (Optional) Change the inbox domain

The address the app shows and the address the webhook classifies against both
read `NEXT_PUBLIC_INBOX_DOMAIN` if it is set, and fall back to
`trips.alyeska.app` otherwise. Set the variable on Vercel if the domain ever
moves; leave it unset otherwise.

## Verifying it works

1. Sign in as a primary in a family with at least one trip, and open `/inbox`.
   Copy the address at the top of the screen.
2. Send a plain text email to that address from a personal account. Wait up to
   a minute for Postmark to relay it.
3. Refresh `/inbox`. The message should appear as a card labelled "Needs a
   person", because the sending address is not yet on any traveler's known
   list. Choose File it and pick a trip to file it onto, or choose Trust
   sender only if the sender is one of the family's travelers and future mail
   from them should be pre-attributed.

If the message does not appear:

- Check Postmark → Server → Activity for the incoming message. If it is not
  there, the MX records are not yet propagating -- give it up to an hour.
- If Postmark received it but the webhook shows a failure, the most likely
  cause is the shared secret. Rotate it in both places and redeploy.

## What the webhook does with the message

For every message that clears the secret check:

1. Looks up the family by the `To:` local part. Unknown local parts get a 200
   response and no work -- Postmark does not need to retry them.
2. Deduplicates on Postmark's `MessageID`. Duplicates get a 200 and no work.
3. Classifies the sender as one of `traveler` (matches a `travelers.email`),
   `forwarder` (matches an entry in `family_forwarders` the primary has
   already trusted), or `unknown`. The classification is written once, at
   receive time, and is what the `/inbox` card colors read off.
4. Stores the message row, then uploads every attachment (up to 25&nbsp;MB
   each) to the `documents` Storage bucket under
   `<family_id>/inbox/<message_id>/<stamp>-<rand>-<safe filename>`, and
   records an `inbox_attachments` row for each.

Filing a message onto a trip, trusting a sender, and throwing a message out
are all done on the client through the three routes under
`/api/inbox/[id]/…`; they carry the user's session and are checked against
family membership by row-level security.
